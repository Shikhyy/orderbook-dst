## f9_dbg_1 (f1_fee_b / m_volume_before_fee)

- **Defect.** Both accounts' volume is increased before the taker fee is computed, so the fee tier is chosen from a volume that already contains the current fill (R-F1).
- **Why the symptom is not obvious.** No report, invariant or conservation check can see it: the FILL report is correct and money is conserved (the fee goes to the vault either way). Only the taker's cash differs, and only for a fill that crosses the tier threshold.
- **Why the fix is unique.** R-F1 says volume is added after the fee is computed, so the single correct place for the two volume lines is after the fee and rebate settlement. Any correct fix reproduces the reference state.

## f9_dbg_2 (f4_waterfall_b / m_no_recheck_after_cancel)

- **Defect.** After stage 1 the breach test is not repeated, so an account whose cancelled orders released enough margin is still liquidated (R-W4).
- **Why the symptom is not obvious.** The symptom is one extra LIQUIDATED report at the last event of an 11-event trace; it does not say which rule was skipped or that stage 1 had cancelled orders first. (The public tests, which the model cannot run, do cover the case.)
- **Why the fix is unique.** R-W4 requires the same breach test with the new free_cash; liquidation only if still in breach. The corrected behaviour is fully determined by R-W2 and R-W4.

## f9_dbg_3 (f5_basket_b / m_forgot_counter_restore)

- **Defect.** A rolled-back basket keeps the advanced order-id counter instead of restoring the whole snapshot (R-A4).
- **Why the symptom is not obvious.** The rolled-back basket itself reports correctly. The first visible effect is an order id that is too large in a later ACCEPTED report, an event after the rollback, so the cause has to be traced back to the rollback path.
- **Why the fix is unique.** R-A4 restores the complete state snapshot; restoring the counter as well is the only way to reproduce the reference order ids.

## f9_dbg_4 (f6_match_b / m_maker_lock_stale)

- **Defect.** A partially filled resting order releases margin to the account but keeps its old stored lock (R-M4 step 4).
- **Why the symptom is not obvious.** The reports are all correct; the symptom is a margin invariant on the resting order after a partial fill. Fully filled orders are fine, so simple fills do not show it, and the visible tests pass.
- **Why the fix is unique.** R-M4 step 4 stores new_lock in the order for both sides of every fill; the condition on leaves has no support in the rules.

## f9_dbg_5 (f7_funding_b / m_residual_not_to_vault)

- **Defect.** The net of the per-account payments (the rounding residual) is computed but never added to the fee vault, so total money drifts by the residual (R-Y3).
- **Why the symptom is not obvious.** The numbers are off by a few micro-units of cash, long after the first FUNDING event that caused it, and the reports are correct. The code that is missing is an omission, so there is no wrong line to point at (an accumulator is left unused, which is the one hint).
- **Why the fix is unique.** R-Y3 states that the net of payments and receipts goes to the fee vault, keeping cash plus vault constant. Booking it is the only conserving fix.

## f9_dbg_6 (f8_adl_b / m_leftover_largest_remainder)

- **Defect.** The leftover units after floor division go to the largest fractional remainders (the textbook method) instead of the largest weights (R-L3).
- **Why the symptom is not obvious.** Shares differ by one unit between the same accounts, only when the weights and remainders rank differently. Money is still conserved, so no invariant fires, and the method used is a plausible one.
- **Why the fix is unique.** R-L3 fixes the ranking: descending weight, ties by ascending account id. No other ordering reproduces the reference.
